# Design: Document Library Management

## 1. Design decisions

### 1.1 删除 = 立即彻底清除(非软删除)

documents 已有生命周期状态(active_only 过滤),但"软删除保留可回看内容"
对本地优先的单用户产品是错的默认:用户删除资料的动机通常是隐私(误传、
敏感、不再需要),"删了还能被翻出来"直接损害信任。因此删除事务执行:

1. 文档状态 → `deleted`(检索范围立即排除);
2. LanceDB 中该 doc_uid 的全部 chunks 删除;
3. 页面图、OCR 产物、转换中间文件、原始上传文件删除;
4. ingestion 状态记录终结。

历史消息中的引用不做改写:证据 chip 渲染为"文档已删除",定位按钮置灰,
预览接口对已删除文档返回明确的 404 语义(不是空白图)。前端不得 mock
"已删除"内容——状态来自服务端事实。

级联一致性:删除在单事务中标记状态,派生物清除允许分步完成但必须幂等、
可从状态重驱动(启动对账复用现有 reconciler 模式);清除完成前文档已
不可检索、不可预览(以状态为准,不依赖文件是否已删)。

### 1.2 重命名只改元数据,不回写历史

标题是文档当前元数据;引用 chip 与证据卡在渲染时按 doc_uid 解析当前标题。
历史消息若内嵌了生成时的标题文本,保持原样(消息是历史事实,不做 Orwell
式改写)。重命名校验:非空、去首尾空白、长度上限(200)。

### 1.3 阅读器复用服务端页图,不引入 pdf.js

**备选对比**:

- **A(选定)服务端页图分页阅读器**:所有格式(PDF/Office/图片/TXT)在
  入库时已统一转为页面并生成页图,preview 接口已存在且带 OCR 坐标数据。
  阅读器 = 分页容器 + 页码导航 + 复用 evidence-preview 的高亮叠加逻辑。
  零新依赖、全格式一致、与证据深链天然同源。
- **B(否决)pdf.js 客户端渲染**:真矢量 PDF 体验,但只覆盖 PDF 一种格式,
  新增重型依赖与双渲染路径(服务端页图仍需为 OCR/高亮保留),Office/图片
  文档仍无阅读器,碎片化。

阅读器交互(v1):页码输入/上一页下一页/总页数、适应宽度、加载占位、
从证据 chip 深链(`?page=N&polygons=...` 或等价路由参数)跳转并高亮。
深链参数由服务端证据事实驱动,前端不自行构造坐标。

## 2. API

```text
PATCH  /documents/{doc_uid}          { title }  → 更新后的文档元数据
DELETE /documents/{doc_uid}          → 202;幂等(重复删除返回成功)
GET    /documents/{doc_uid}          → 元数据 + page_count(阅读器入口)
GET    /documents/{doc_uid}/preview/{page}   (既有,增加已删除文档的明确错误语义)
```

所有路由校验项目/用户归属(与现有文档路由同一守卫)。

## 3. Testing

- 删除后:检索无命中、scope 列表不含该文档、preview 返回删除语义、
  历史引用渲染占位、重复删除幂等、派生物清除可对账重驱动。
- 重命名后:列表/引用 chip/证据卡显示新标题,历史消息文本不变。
- 阅读器:分页导航、格式覆盖(PDF+TXT 至少)、证据深链跳页并高亮、
  已删除文档打开阅读器得到服务端错误态。
